# Идеи и задачи на будущее

Этот файл хранит идеи, которые пока не входят в ближайший scope, но должны
остаться в roadmap проекта.

## 1. Видео в постах и сообщениях

### Цель

Разрешить загружать видео так же, как сейчас загружаются фотографии, но
готовить несколько вариантов качества для разных устройств и скорости сети.

### Предлагаемая архитектура

- отдельный сервис обработки видео на Go;
- FFmpeg как worker-инструмент транскодирования;
- исходный файл сохраняется отдельно от производных вариантов;
- фоновые jobs через Kafka или отдельную очередь задач;
- статусы обработки: `uploaded`, `processing`, `ready`, `failed`;
- варианты качества, например 360p, 720p и оригинал;
- HLS/DASH для потокового воспроизведения вместо загрузки целого файла;
- превью-кадр и метаданные: длительность, размер, разрешение, codec;
- повторная обработка и DLQ для неудачных jobs;
- очистка исходников и неиспользуемых вариантов по retention policy.

### Что нужно добавить

- отдельный media/video domain и API статуса обработки;
- таблицы video assets и renditions;
- object storage layout для исходников, previews и renditions;
- лимиты размера, длительности и допустимых форматов;
- антивирусную/безопасностную проверку файла;
- integration-тесты с FFmpeg и contract-тесты Kafka-сообщений;
- метрики: processing duration, failures, queue lag, transcoded bytes.

### Риски

- FFmpeg требует CPU, RAM и дисковое место;
- транскодирование нельзя выполнять внутри HTTP-запроса;
- исходник и варианты должны быть идемпотентными;
- понадобится lifecycle policy для хранения больших файлов;
- сервису нужна отдельная autoscaling/backpressure стратегия.

## 2. Аудио- и видеозвонки через WebRTC

> Статус: базовый one-to-one signaling-контур реализован в Go-сервисе
> `services/call-signaling`. Подробное описание запуска и протокола — в
> [`docs/webrtc-go-migration.md`](webrtc-go-migration.md). Ниже остаются
> следующие production-этапы.

### Цель

Добавить звонки один-на-один и в будущем групповые звонки:

- аудиозвонок;
- видеозвонок;
- mute/unmute микрофона;
- включение/выключение камеры;
- переключение устройств;
- завершение звонка;
- состояние звонка в профиле и messenger UI.

### Базовые компоненты

- WebRTC в браузере для передачи media streams;
- WebSocket/SSE или отдельный signaling-сервис для SDP и ICE-кандидатов;
- STUN для определения маршрута;
- TURN для случаев, когда прямое соединение невозможно;
- отдельный call session model с состояниями `ringing`, `connecting`,
  `connected`, `ended`, `failed`;
- permissions для камеры и микрофона;
- уведомления о входящем звонке через realtime-канал.

### Важное ограничение

WebRTC сам по себе не устанавливает звонок. Он передаёт media между клиентами,
но приложению всё равно нужен signaling-канал для обмена offer, answer и ICE.
Для production-подобного сценария TURN-сервер обязателен, потому что не все
пользователи смогут соединиться напрямую.

### Этапы реализации

1. Аудиозвонок один-на-один в пределах одного браузера/локальной сети.
2. Signaling через существующий WebSocket и call session в PostgreSQL.
3. STUN/TURN и проверка соединений из разных сетей.
4. Видеозвонок и управление устройствами.
5. Входящие звонки, timeout, busy/reject и восстановление соединения.
6. Групповые звонки через SFU, например Janus, LiveKit или mediasoup.

### Что не стоит делать в первой версии

- не передавать аудио/видео через backend;
- не хранить media stream в Kafka;
- не пытаться сделать групповые звонки через mesh WebRTC;
- не добавлять запись звонков без отдельного согласия пользователей и policy.

### Риски и безопасность

- проверять права пользователей до отправки call invite;
- учитывать блокировки и настройки приватности;
- не раскрывать signaling-сообщения посторонним клиентам;
- ограничивать время жизни call session;
- защищать TURN credentials и использовать временные токены;
- продумать consent для записи и хранения звонков;
- собирать только техническую аналитику: длительность, outcome, качество,
  packet loss и reconnects.

## Связь с текущей архитектурой

- PostgreSQL остаётся источником состояния постов, пользователей, чатов и call
  sessions;
- Kafka используется для domain/integration events, уведомлений и фоновых
  video jobs;
- Go messaging WebSocket остаётся realtime-каналом сообщений, а отдельный Go-
  WebSocket `call-signaling` является signaling-транспортом WebRTC;
- отдельные Go-сервисы не должны становиться зависимостью HTTP API;
- для видео и звонков нужны отдельные healthcheck, metrics, retry policy и DLQ,
  если операция асинхронная;
- все операции должны учитывать текущие privacy settings и RBAC.
